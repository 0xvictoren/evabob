# Hosted Arc testnet on Render

Evabob testnet is defined by the root [`render.yaml`](../render.yaml) Blueprint.
It creates three resources in Frankfurt:

| Render resource | Type | Purpose |
|---|---|---|
| `evabob-api-testnet` | paid Node web service, one instance | Hono API, Circle/Arc integration and durable avatar uploads |
| `evabob-web-testnet` | paid Node web service | Next.js public `/pay/{id}` and `/claim` pages |
| `evabob-refunds-testnet` | cron, every 5 minutes | Calls `/internal/cron/tick?refunds=1`: due held-payment releases, abandoned-bridge completion, reminders, expired-hold refunds |

The smallest paid web plan is intentional. The API needs a persistent disk,
which Render does not offer on free web services. The public payment service is
also kept awake so payment and claim links do not incur a free-tier cold start.
The Blueprint does not deploy MongoDB: Atlas remains the authoritative store.

## What is automatic

- Render assigns both `*.onrender.com` HTTPS origins and wires them between the
  web and API services without copying URLs by hand.
- `ALLOW_HEADER_AUTH=false`, testnet boundaries and exact browser CORS are set.
- A 1 GB encrypted persistent disk is mounted at `/var/data`; the app writes
  avatars and local recovery mirrors below `/var/data/evabob`.
- `CRON_SECRET` is generated by Render and shared internally with the cron.
- The in-process refund timer is disabled on Render, preventing duplicate runs.
- `/health/ready` gates API health and `/api/health` gates public-web health.
- All money features start disabled. Enable each flag only after its hosted
  acceptance test passes.

## 1. Validate the local secret file

The app reads `server/.env` only on your machine. Run:

```powershell
Set-Location server
npm run validate:render-env
```

This reports missing or structurally invalid variable names without printing
any value. `server/.env` is ignored by Git and must stay that way.

## 2. Create the Render Blueprint

1. In Render, choose **New > Blueprint** and connect the Evabob GitHub repo.
2. Select the `main` branch and the root `render.yaml` file.
3. During the first sync, provide every value marked `sync: false`. Copy only
   the matching keys from `server/.env`; do not upload the file to Git.
4. Check the estimated paid resources before applying the Blueprint.
5. Keep the API at exactly one instance. The persistent disk and current
   single-writer snapshot model do not support horizontal scaling.

Do not copy local-only values such as `PORT`, `CORS_ORIGINS`, `API_PUBLIC_URL`,
`APP_PUBLIC_URL`, `NODE_ENV`, `DATA_DIR`, `ALLOW_HEADER_AUTH` or
`RUN_INTERNAL_REFUND_JOB` into Render. The Blueprint owns them.

If a new `sync: false` variable is added after the first Blueprint sync, Render
does not prompt again. Add it manually on that service's **Environment** page.

## 3. Allow Render to reach Atlas

After Render creates the API service:

1. Open `evabob-api-testnet` and choose **Connect > Outbound**.
2. Copy every listed CIDR range.
3. In Atlas, open **Network Access** and allow those exact ranges.
4. Use an Atlas user scoped to the `evabob_testnet` database.
5. Confirm `GET /health/ready` reports `database: connected` and
   `persistence: mongo`.

Avoid leaving Atlas open to `0.0.0.0/0`. A dedicated Render outbound-IP set is
optional later; the ordinary region ranges are sufficient for internal testnet.

## 4. Initial `*.onrender.com` deployment

The Blueprint service names normally produce:

```text
https://evabob-api-testnet.onrender.com
https://evabob-web-testnet.onrender.com
```

If Render changes a name because it is already taken, use the actual URL in
the mobile defines. Copy
`mobile/dart_defines.render.example.json` to a local testnet defines file and
replace both origins if needed. Never put a server secret in Flutter.

Add the actual public-web origin to Dynamic's allowed origins. Then verify:

```text
GET https://evabob-api-testnet.onrender.com/health/live
GET https://evabob-api-testnet.onrender.com/health/ready
GET https://evabob-api-testnet.onrender.com/v1/config/public
GET https://evabob-web-testnet.onrender.com/api/health
```

Manually trigger `evabob-refunds-testnet` once from its **Runs** page and check
that it exits successfully.

Run the repeatable public smoke check from `server`:

```powershell
$env:API_PUBLIC_URL = "https://evabob-api-testnet.onrender.com"
$env:APP_PUBLIC_URL = "https://evabob-web-testnet.onrender.com"
npm run smoke:render
```

## 5. Custom testnet domains

After the default deployment is healthy, add these custom domains in Render:

```text
Web: https://testnet.evabob.app
API: https://api-testnet.evabob.app
```

Create the DNS records Render displays. After certificates are active, replace
these API environment values and redeploy:

```text
API_PUBLIC_URL=https://api-testnet.evabob.app
APP_PUBLIC_URL=https://testnet.evabob.app
CORS_ORIGINS=https://testnet.evabob.app
```

Replace the web service's `EVABOB_API_BASE_URL` and
`NEXT_PUBLIC_API_BASE_URL` with the custom API origin. Also replace the mobile
`API_BASE_URL` and `DYNAMIC_APP_ORIGIN`, and add the custom web origin to
Dynamic. The Render-generated values do not automatically switch when a custom
domain is attached.

## 6. Mobile testnet build

The mobile build contains public identifiers only:

```text
API_BASE_URL=https://api-testnet.evabob.app
DYNAMIC_APP_ORIGIN=https://testnet.evabob.app
AUTO_DEMO=false
```

Circle API keys, signer keys, Mongo URIs, SMTP passwords, Dynamic API tokens
and `CRON_SECRET` must never be compiled into Android or iOS.

The final `com.evabob.app` package/bundle identifier, Android App Links, iOS
Universal Links, Play Internal Testing and TestFlight still require explicit
project/account setup. Keep `evabob://` until the custom domain and both store
records exist.

## Hosted acceptance gate

Before enabling a feature flag:

1. Confirm API and web health checks are green after a fresh deploy.
2. Confirm an allowed browser origin receives CORS headers and an unrelated
   origin does not.
3. Restart the API and verify Mongo restoration and avatar persistence.
4. Verify Dynamic renewal, logout, account switching, expiry and UCW isolation.
5. Verify `/pay/{id}` and `/claim` on a device without Evabob installed.
6. Enable only the single feature being tested, complete its failure matrix,
   then leave it enabled only if every state reconciles correctly.

## Scheduled work — `/internal/cron/tick`

Some things must happen on time with nobody watching: a job hold whose 7
days are up releases to the worker, a cooling-off payment goes after its 10
minutes, a bridge abandoned for 40 minutes is finished by the server, and
reminders go out. One authenticated route does all of it:

```
GET /internal/cron/tick            # held payments + abandoned bridges
GET /internal/cron/tick?refunds=1  # …plus the expired-hold refund sweep
Authorization: Bearer $CRON_SECRET
```

Every step re-checks the chain before moving money, so running it twice, or
late, only repeats or delays work. The same work also runs whenever the people
involved open their held payments or bridge jobs, so a missed schedule delays
a release rather than losing it.

| Host | How it is scheduled |
|---|---|
| **Local** (current — the API is not hosted yet) | The server runs the same work every minute in process unless `RUN_INTERNAL_REFUND_JOB=false`. No cron is needed. |
| **Render** (prepared, not deployed) | The `evabob-refunds-testnet` cron runs `npm run cron:tick` every 5 minutes. |
| **Vercel** (prepared, not deployed) | `server/vercel.json` declares a daily cron, the most frequent a free plan accepts. Set `CRON_SECRET` in the project's environment and Vercel sends it automatically. On a Pro plan use `*/5 * * * *`, or point an external scheduler at the route every 5 minutes. |

A 10-minute cooling-off payment only goes on time if something runs within a
few minutes of it becoming due — the scheduler, or the sender watching the
countdown screen (which asks the server when the timer ends).

## Scaling boundary

The store is still an in-memory snapshot mirrored to Mongo, but two limits
were removed on 2026-09-18:

- **The 16 MB ceiling.** The snapshot is written as chunk documents under a
  small head document that is switched atomically to each new generation.
  While the state is under 12 MB the head also carries an inline copy, so a
  server still running the previous release can read it.
- **One writer only.** Each save is conditional on the generation the process
  loaded, so a second instance can no longer silently overwrite the first.
  Each request first checks the head (one small read) and reloads if another
  instance saved. A save that loses a race fails with `503
  persistence_unavailable` instead of overwriting. On Vercel the writer lease
  is advisory for that reason; elsewhere it is still exclusive.

Profile photos are stored in Mongo, not on the API's disk.

Still to do before real traffic: financial records as individual Mongo
documents with per-record atomic writes (so concurrent requests on different
instances do not contend for one snapshot), and an external contract audit.
